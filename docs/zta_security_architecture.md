# MacOSUI ゼロトラストセキュリティ（ZTA）設計アーキテクチャ

本ドキュメントは、MacOSUI に実装されているゼロトラスト・アーキテクチャ（ZTA）に基づく認可モデルの設計、および PDP（方針決定点）と PEP（方針強制点）の定義と実装方針について記述します。

---

## 1. ゼロトラスト認可（ZTA）モデルの基本設計

MacOSUI は、境界型セキュリティ（ネットワークの内側は安全とする考え方）を廃止し、すべてのアクセス要求（リクエスト）に対して「決して信頼せず、常に検証する」ゼロトラストモデルを採用しています。

このモデルを実現するため、認可基盤を **PDP (Policy Decision Point)** と **PEP (Policy Enforcement Point)** に分離し、ポリシーの動的な変更と正確な強制を保証します。

```
[ クライアント (Browser) ]
         │
         ▼  (HTTP リクエスト / API 呼び出し)
┌──────────────────────────────────────────────┐
│  PEP (Policy Enforcement Point: 方針強制点)  │
│  ※ 共通 Express ミドルウェア                 │
└──────┬───────────────────────────────────────┘
       │
       ├─ (問合せ: このユーザーは許可されているか？)
       ▼
┌──────────────────────────────────────────────┐
│  PDP (Policy Decision Point: 方針決定点)   │
│  ※ DB 内のポリシー定義 (RBAC_POLICIES)      │
└──────┬───────────────────────────────────────┘
       │
       ▼ (判定結果: OK / NG)
┌──────────────────────────────────────────────┐
│  エンドポイント (ビジネスロジック)           │
│  ※ deepResearch.cjs など                     │
└──────────────────────────────────────────────┘
```

---

## 2. PDP (Policy Decision Point: 方針決定点)

### 2.1 役割と定義
PDP は、アクセス権の付与ルール（ポリシー）を一元的に管理し、アクセス要求がポリシーに適合しているかを判断する意思決定機関です。

### 2.2 実装構造
*   **ポリシーの保存先**: SQLite データベースの `settings` テーブル内の `RBAC_POLICIES` キー（JSON 形式）。
*   **ポリシー構造 (RBAC)**:
    役割（Role）ごとに許可するウィジェット（`allowed_widgets`）、アクション（`allowed_actions`）、使用可能なAIモデル（`allowed_models`）を定義します。
*   **動的アップデート (マイグレーション)**:
    システム起動時に `db.cjs` の `autoActivate()` ロジックが走り、既存のポリシー構造を検査します。新機能（例: `app:deep-research`）の権限が既存ポリシーに欠落している場合、自動的にマイグレーション（ルール同期）を実行し、ポリシーの一貫性を保ちます。

---

## 3. PEP (Policy Enforcement Point: 方針強制点)

### 3.1 役割と定義
PEP は、ユーザーからのリクエストをインターセプトし、PDP の決定（許可/拒否）を**強制**する役割を持ちます。

### 3.2 実装の共通化ルール (一元化ポリシー)
認可の脆弱性を防ぐため、**「PEP 判定ロジックはルートハンドラ内に個別にインライン実装せず、共通ミドルウェアとして一元管理する」** という設計原則を採用します。これによって、コードコピーによる判定基準のズレ（二重基準）を永久に排除します。

#### ① 共通ウィジェット認可ミドルウェア (`requireWidgetAccess`)
Webコンテナ（API）の全エンドポイントの入り口で、ユーザーが該当アプリを起動できるかを強制します。
```javascript
// server/index.cjs で一元定義
app.use('/api/research', requireWidgetAccess('app:deep-research'), deepResearchModule.router);
```
ユーザーの持つマルチロール（カンマ区切り）を自動で分割パースし、いずれかのロールがウィジェット権限を持っていれば通過させ、持っていなければ ZTA 監査ログにブロックイベントを記録して `403 Forbidden` を返します。

#### ② 共通アクション認可ミドルウェア (`requirePermission`)
データの操作や設定変更など、特定のビジネスアクションの実行を強制します。
```javascript
app.put('/api/users/:id/role', requirePermission('action:manage_roles'), (req, res) => { ... });
```

---

## 4. 設計変更履歴 (仕様統一)

*   **変更前 (インラインPEPとの二重基準)**:
    `/api/research` ルート全体が `requireWidgetAccess('app:deep-research')` で一元保護されていたにもかかわらず、中の `/api/research/start` エンドポイント内部で個別にロール判定を再実装していました。このインライン判定がマルチロール（カンマ区切り）のパースに対応していなかったため、認可判定の不整合が生じる原因となっていました。
*   **変更後 (共通PEPへ一本化)**:
    エンドポイント内のインライン判定コードを完全に撤去し、ルート全体の共通ミドルウェア `requireWidgetAccess` に認可の強制（Enforcement）を一任しました。これにより、仕様の揺れをなくし、ZTA モデルとしての堅牢性と保守性を向上させました。
