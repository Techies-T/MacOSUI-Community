# MCP サーバーセキュリティ標準設計ガイドライン (ZTA/A2A 準拠)

本ドキュメントは、プロジェクト内において新規に MCP (Model Context Protocol) サーバーを構築、または既存のサーバーを拡張する際に、強制適用されるセキュリティおよびトランスポートの標準仕様ガイドラインです。

ゼロトラストアーキテクチャ (ZTA) に適合させ、各エージェントおよびサービス間の安全な連携を保証するため、以下の設計基準を必ず遵守してください。

---

## 1. ゼロトラスト認証 (ZTA / A2A Token Verification)

各エージェント、外部ウィジェット、および MCP サーバーへの接続・リクエストは、Agent-to-Agent (A2A) 認証フローに基づいて、厳格に暗号化および検証されなければなりません。

### ① A2A トークンの発行とトークン交換 (RFC 8693 & OAuth 2.0)
* **MacOSUI 本体が提供する認証エンドポイント**: `POST /api/auth/token-exchange`
* **動作仕様**:
  1. **標準のトークン交換 (Token Exchange)**:
     * ログイン中のユーザー認証トークン（Cookie）を元に、特定のウィジェットやエージェント専用に、一時的かつ最小権限（ダウンスコープ）された JWT (Agent Token) を発行・請求します。
     * リクエストパラメータ: `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `audience=<target>`
  2. **システム間直接 A2A 認証 (Client Credentials)**:
     * ログインユーザーを介さない内部システムや内蔵 MCP（Knowledge Base等）が、自律的に認証を完了してセキュア通信を行うためのフローです。
     * リクエストパラメータ: `grant_type=client_credentials`, `client_id=macos-ui-internal-client`, `client_secret=<DB_ENCRYPTION_KEY>`, `audience=<target>`
     * **認証仕様**: `client_secret` としてコンテナ内の安全な環境変数 `DB_ENCRYPTION_KEY`（暗号マスターキー）を検証することで、外部からのなりすましを防止します。
* **トークンの有効期限**:
  * 発行される JWT トークンの有効期限は **1 時間 (3600秒)** とし、発行完了のレスポンスに `expires_in: 3600` を明記します。

### ② JWT 署名と有効期限の厳格検証 (ZTA PEP)
* **ミドルウェアでの検証**:
  * 本体または内蔵 MCP サーバーがリクエストを受ける際、トークンが正しく `JWT_SECRET` で署名されていること、および有効期限内であることを確認します。
  * 対象オーディエンス (`aud`) やトークンタイプ (`type === 'agent_token'`) などの検証を行い、適合しないリクエストはすべて `401 Unauthorized` または `403 Forbidden` で即座に遮断します。
  * システム内蔵 MCP サーバー（`/api/mcp/knowledge`）は、JWT 署名検証を行う `requireAgentOrUserAuth` ミドルウェアで保護し、認証なしの接続（No Auth）を一切拒否します。

## 2. トランスポート通信の完全HTTPS（TLS）強制

ZTA において「ネットワーク境界は信頼しない」ため、すべてのデータ転送は暗号化（HTTPS / WSS）されなければなりません。

* **暗号化ポリシー**:
  * 開発環境における `localhost` または `127.0.0.1` での稼働を除き、MacOSUI に登録・編集、および疎通テストを行うすべての MCP エンドポイント（`endpoint_url`）および認可トークンエンドポイント（`token_url`）は、**必ず `https://` で始まる安全なドメイン通信であることをシステムレベルで強制**します。
  * バリデーションチェックにより、非暗号化 HTTP プロトコルを用いた外部登録・テスト要求は、API ゲートウェイが `400 Bad Request` にて即座にブロックします。

---

## 3. トークン有効期限切れへの自動対応 (サイレントリフレッシュ)

接続するクライアント（またはエージェント）がバックグラウンドで自動的に新しいトークンを再取得（サイレントリフレッシュ）できる設計にします。

* **動作仕様**:
  * トークンの有効期限切れエラー (`invalid_token`) が返された場合、クライアント側が再度 `client_id` と `client_secret` を用いてトークンを再取得し、自動で処理を再試行（リトライ）できる構成を考慮した設計にします。
  * サーバー側は、これらの一時的な再接続をスムーズに受け入れられるよう、ステートレスな設計を心がけます。

---

## 4. SSE (Server-Sent Events) トランスポート通信

MCP メッセージのやり取りには、標準の stdio 方式ではなく、HTTP 経由の双方向通信である **SSE (Server-Sent Events) 方式** を採用します。これにより、コンテナ間通信や異なるネットワーク間でのセキュアなやり取りを実現します。

### ① 接続エンドポイント (`GET /sse`)
* クライアントから ZTA 認証トークン（クエリパラメータ等）を伴う接続要求を受け、持続的なイベントストリームを確立します。
* 接続時に一意の `sessionId` (Session ID) を発行し、トランスポートマップでセッションを永続的に管理します。

### ② メッセージ送信エンドポイント (`POST /message`)
* クライアントが `sessionId` を指定して MCP 要求 (JSON-RPC) をポストします。
* サーバー側は認証ヘッダー (`Authorization: Bearer <token>`) を検証し、該当セッションの SSE ストリームを通じて MCP レスポンスをプッシュします。

---

## 5. データベースの整合性と親ストーリー連動

アジャイル開発進捗などの共有データを扱う場合、データの不整合を防ぐため、以下の自動整合ロジックを実装します。

* **状態変化の制限**:
  * レビュー対象などのデリケートな変更（承認など）を行う場合、対象レコードの現在の状態（例: `status === 'review'`) を事前チェックし、不正な遷移を拒否する安全ブレーキ機能を実装します。
* **親要素への自動伝播**:
  * サブタスク（詳細タスク）の状態が変化した際、親バックログ（ユーザーストーリー）の状態を自動再評価し、全体の完了・進行状況を自動同期します。

---

## 6. 推奨する技術スタックとモジュール構成 (Node.js テンプレート)

* **Express**: 認証・トークン発行・SSE エンドポイントのルーティング管理。
* **@modelcontextprotocol/sdk**: 公式 MCP SDK (`Server`, `SSEServerTransport`) を使用。
* **jsonwebtoken**: JWTの生成・検証。
* **sqlite3**: 軽量でファイル永続性のある SQLite の利用。自動対応 (サイレントリフレッシュ)
